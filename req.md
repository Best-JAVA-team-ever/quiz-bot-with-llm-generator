# Quiz Bot with LLM Question Generator. Требования

## 1. Введение

Система представляет собой чат-бота с возможностью проведения тестов. Основные функции:
- Управление базой вопросов (ручное добавление и генерация через LLM).
- Проведение одиночных викторин по случайным вопросам или вопросам из определённых тематических доменов.
- Автоматическая рассылка вопросов по расписанию.
- Получение развёрнутых объяснений к ответам от LLM.
- Учёт очков пользователя, в том числе в разрезе доменов (тегов).
- Групповые викторины, таблицы лидеров и адаптивная сложность.

---

## 2. Функциональные требования

### 2.1. Управление вопросами (Question Management)

#### 2.1.1. Ручное добавление вопроса
- Система должна предоставлять администратору (или привилегированному пользователю) интерфейс для добавления вопроса.
- Обязательные поля вопроса:
  - **Текст вопроса** (строка до 500 символов).
  - **Правильный ответ** (строка до 200 символов).
  - **Теги/домены** (массив строк, минимум 1 тег).
- Опциональные поля:
  - **Уровень сложности** (целое число от 1 до 5, по умолчанию 3).
  - **Пояснение к ответу** (строка до 1000 символов).
- Вопрос должен сохраняться в базе данных с уникальным идентификатором и меткой времени создания.

#### 2.1.2. Генерация вопросов с помощью LLM
- Пользователь с соответствующими правами может запросить генерацию вопроса, указав:
  - **Тему/домен** (обязательно, один или несколько тегов).
  - **Желаемый уровень сложности** (1–5, по умолчанию 3).
- Система отправляет промпт к выбранной LLM (например, OpenAI API, локальная модель). Промпт должен включать инструкцию сгенерировать вопрос в заданной предметной области, указанной сложности, с одним правильным ответом и кратким пояснением.
- Ответ LLM должен быть структурирован (JSON), содержать:
  ```json
  {
    "question": "текст вопроса",
    "answer": "правильный ответ",
    "explanation": "пояснение",
    "tags": ["тег1", "тег2"]
  }
  ```
- Перед сохранением система должна валидировать полученный JSON и наличие всех обязательных полей.
- Сгенерированный вопрос помечается флагом `generated_by_llm = true` и сохраняется аналогично ручному.

#### 2.1.3. Просмотр, обновление и удаление вопросов
- Должен быть интерфейс для постраничного вывода списка вопросов с фильтрацией по:
  - Тегу (точное совпадение).
  - Уровню сложности (диапазон).
  - Источнику (ручной / LLM).
- Для каждого вопроса доступны действия:
  - **Редактирование** всех полей, кроме идентификатора.
  - **Удаление** (мягкое удаление с возможностью восстановления или полное удаление по требованию).
- При удалении вопроса, если на него уже были даны ответы пользователями, статистика по ответам должна сохраняться, но вопрос исключается из будущих выборок.

### 2.2. Функциональность викторины

#### 2.2.1. Запрос случайного вопроса
- Любой пользователь может выполнить команду, запрашивающую случайный вопрос из всей базы.
- Система выбирает случайный вопрос, исключая ранее показанные данному пользователю за последние N дней (N настраивается, по умолчанию 7). Если исключение невозможно (все вопросы были показаны), выборка происходит без ограничений.

#### 2.2.2. Запрос случайного вопроса из определённого домена
- Пользователь может указать один или несколько тегов.
- Система выбирает случайный вопрос, имеющий **хотя бы один** из указанных тегов.
- Логика исключения ранее показанных вопросов аналогична п.2.2.1.

#### 2.2.3. Автоматическая рассылка по расписанию
- Администратор (или владелец группы) может настроить расписание отправки одного случайного вопроса в чат/канал.
- Параметры расписания:
  - Частота (ежедневно, еженедельно, по определённым дням недели).
  - Время отправки (часы:минуты, с учётом часового пояса, задаваемого для чата).
  - Домен (опционально, если не указан – вопрос из всей базы).
- Система должна гарантировать, что в одно и то же время в один чат отправляется не более одного вопроса.

#### 2.2.4. Объяснение ответа с помощью LLM
- После того как пользователь дал ответ на вопрос, система сообщает, верен ли ответ.
- Независимо от правильности ответа, пользователь может запросить развёрнутое объяснение командой (например, `/explain`).
- Если у вопроса уже есть поле `explanation`, оно выводится сразу.
- Если объяснение отсутствует, система обращается к LLM с промптом, включающим текст вопроса, правильный ответ и просьбу дать краткое, но содержательное объяснение (до 1500 символов).
- Полученное объяснение сохраняется в базу данных для повторного использования и выводится пользователю.

### 2.3. Управление счётом

#### 2.3.1. Отображение счёта пользователя
- Каждый пользователь имеет общий счёт (число очков), который увеличивается на 1 за каждый правильный ответ.
- Команда для проверки счёта возвращает текущее значение.

#### 2.3.2. Сброс счёта
- Пользователь может сбросить свой общий счёт до нуля командой. Требуется подтверждение (например, кнопка «Да, сбросить»).

#### 2.3.3. Отображение счёта по доменам
- Для каждого пользователя ведётся отдельный подсчёт правильных ответов по каждому тегу (домену).
- Команда запроса статистики по доменам должна возвращать список тегов с соответствующим количеством правильных ответов, отсортированный по убыванию.

## 3. Нефункциональные требования

### 3.1. Производительность
- Время ответа бота на команду (без учёта обращения к LLM) не должно превышать 2 секунды для 95% запросов.
- Обращение к LLM может занимать до 20 секунд, при этом пользователь должен получать индикатор выполнения (например, «Генерирую вопрос, подождите...»).
- Система должна выдерживать не менее 20 одновременных активных пользователей без деградации производительности.

### 3.2. Надёжность и доступность
- Доступность сервиса – не ниже 99,5% (в месячном исчислении, исключая плановое обслуживание).
- При сбое внешнего LLM-сервиса система должна корректно обрабатывать ошибки и возвращать пользователю понятное сообщение с предложением повторить позже.

### 3.3. Безопасность
- Взаимодействие с платформой мессенджера должно происходить по HTTPS.
- Ключи API для LLM и других внешних сервисов должны храниться в защищённом виде (переменные окружения, секретные хранилища).
- Все пользовательские данные (счета, история ответов) должны быть доступны только владельцу и администраторам системы.

### 3.4. Масштабируемость
- Архитектура должна позволять горизонтальное масштабирование компонентов, работающих с БД и очередями.
- Вызовы LLM должны быть вынесены в отдельный асинхронный сервис или очередь, чтобы не блокировать основной поток обработки сообщений.

### 3.5. Логирование и мониторинг
- Все действия по изменению данных (добавление/редактирование вопросов, настройка расписаний) должны логироваться с указанием инициатора и времени.
- Должен вестись мониторинг использования LLM API (количество запросов, задержки, ошибки).

## 4. Допущения и ограничения

### • Внешний LLM API
- Для генерации вопросов и объяснений используется внешний LLM-сервис.
- При исчерпании квот или сбоях API пользователю возвращается сообщение об ошибке с предложением повторить позже.
- Для защиты от превышения лимитов запросы к LLM ставятся в очередь с регулировкой частоты.

### • Качество генерируемого контента
- Сгенерированные LLM вопросы могут содержать фактические неточности. Система не гарантирует абсолютную достоверность контента.
- Предусмотрена возможность пометки некорректного вопроса (для будущего исправления).

### • Ограничения данных
- Групповой счёт ведётся отдельно от персонального и не синхронизируется с ним.

## 5. Технический стек

- Язык программирования: Java 25
- Фреймворк: Spring Framework 7
- Сборка: Gradle
- База данных: MongoDB
- Контейнеризация: Docker, Docker Compose
- Публикация образа: образ должен быть загружен на Docker Hub
- Telegram API: используется для приема команд и отправки ответов
- LLM API: GigaChat

## 6. Требования к документации и тестированию

### 6.1. Документация
По завершении разработки должны быть предоставлены следующие артефакты:
1. **README.md** – описание проекта, инструкции по развёртыванию и конфигурации, перечень всех команд бота.
2. **Архитектурная схема** (в формате диаграммы) с указанием основных компонентов и их взаимодействия.

### 6.2. Тестирование
Требования к тестированию включают следующие уровни:

#### 6.2.1. Модульное тестирование
- Покрытие unit-тестами основных сервисов:
  - Логика выбора случайного вопроса (с фильтрацией по тегам и истории показов).
  - Подсчёт очков и статистики по доменам.
  - Валидация структуры ответа LLM.

#### 6.2.2. Интеграционное тестирование
- Проверка взаимодействия с БД (сохранение, обновление, удаление вопросов).
- Проверка корректной работы расписания (использование фиктивного таймера).
- Тестирование заглушенного LLM-клиента для симуляции успешных и ошибочных ответов.

#### 6.2.3. Функциональное (end-to-end) тестирование
- Полные сценарии поведения пользователя:
  - Регистрация (присоединение к боту), запрос случайного вопроса, ответ, просмотр счёта.
  - Создание группы, приглашение участника, запуск группового вопроса по расписанию, проверка группового счёта.
  - Генерация вопроса через LLM (с реальным API в тестовом окружении).
